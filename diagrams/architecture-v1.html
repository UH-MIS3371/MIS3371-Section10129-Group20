Three-Tier Architecture: Patient Referral

MIS 3371  |  Week 3 Capstone Design Checkpoint  |  Team TPS_3371_TEAM_20  |  Patient Referral Management System

Diagram

Presentation

  • Referral form for the referring provider
  • Review queue for receiving department staff
  • Status lookup for the referral coordinator
  • Basic client-side checks: required fields present, a service selected
  • Displays confirmation, current status, and decision reasons back to the user

Application logic

  • Re-validates required fields and the duplicate check server-side
  • Routes the referral to the department that offers the requested service
  • Enforces the allowed state transition list
  • Assigns the referral ID on creation
  • Computes the overdue flag against the review-time threshold
  • Enforces role-based permissions (who can accept, reject, schedule, or cancel)

Data

  • Stores the referral record as the official system of record
  • Stores department and service routing rules
  • Logs every status change (old state, new state, who, timestamp) in an immutable history table
  • Persists submitted_at, updated_at, and all decision reasons

Responsibility notes

ResponsibilityTierNote
Collect input / immediate feedbackPresentationThe form checks that fields are filled in, but this check is a convenience, not the source of truth.
Critical validationApplication logicRequired-field and duplicate-referral checks run again on the server. A request sent directly to the API, bypassing the form, is checked the same way.
Business rulesApplication logicDepartment routing and the allowed state transitions are enforced here, not in the browser. This is the one rule that must stay authoritative on the server: nothing on the client can move a referral to Accepted, Scheduled, or Completed directly.
Audit / historyDataEvery status change is written to a history table that the application layer can append to but never edit or delete. That immutability is the audit requirement this design depends on.
Persist official recordDataThe database, not the browser session or the application server's memory, is the record that survives a restart.

Exception / failure path

If the application server enforced the state transition rules only through the UI and a request came in through a script that skipped the review step, an unreviewed referral could reach Scheduled. The application layer rejects any transition that isn't on the allowed list, regardless of where the request came from, and logs the rejected attempt.
